## Learnings

- Slack supports one table per message. The official composition example puts its top-level table after the preceding block. The API permits 100 rows including the header, 20 cells per row, and 10,000 characters across all table cells in a message. The config schema permits unbounded rosters, so the adapter enforces these limits at posting time. [Slack table reference](https://docs.slack.dev/reference/block-kit/blocks/table-block) · [Slack Block Kit patterns](https://github.com/slackapi/slack-skills-plugin/blob/main/skills/block-kit/references/common-patterns.md#data-table-m)
- `chat.postMessage` requires omitting `markdown_text` when using `blocks` or `text`. Notifications and screen readers use the supplied top-level fallback. Slack recommends 4,000 characters and warns longer text may split, with truncation above 40,000. The adapter bounds the escaped fallback at 40,000 and the table independently at 10,000. Live rendering of very large notices remains unverified. [Slack chat.postMessage reference](https://docs.slack.dev/reference/methods/chat.postMessage)
- Rich text represents links, broadcasts and mentions as distinct typed elements. A text element holds the literal string and can set `style.code`. The table uses raw text for the other columns. [Slack rich text section reference](https://docs.slack.dev/reference/block-kit/block-elements/rich-text-section-element) · [Slack text element reference](https://docs.slack.dev/reference/block-kit/block-elements/text-element)
- Slack reads consume top-level text. The reply transcript and `slack_history` include notice text, the listening snapshot filters notices out, and the picker reads the selected message's text. The picker starts a round with an addressing-only event, so the posted question or quote must be present in the text returned from Slack.
